# DB 도입 아키텍처 논의

- 상태: 논의 진행
- 최초 기록일: 2026-06-26
- 목적: Cafe24 API 실시간 조회 중심 구조에서 DB를 도입할 시점, 책임 분리, 전환 순서를 계속 업데이트하며 기록한다.

## 1. 현재 인식

현재 구현은 별도 DB 없이 Cafe24에서 데이터를 받아와 화면 계산, 매핑, 세트상품 구성, Excel 다운로드를 처리하는 구조다.

초기에는 이 구조가 적절했다. Cafe24를 단일 원천으로 두면 구현이 빠르고, 별도 저장소의 정합성 문제를 피할 수 있었다. 하지만 상품코드 화면이 다음 단계로 커지면서 DB 도입을 검토할 시점이 되었다.

- 매핑 규칙이 생겼다.
- 세트상품 구성 편집이 생겼다.
- 사용자 변경사항이 생겼다.
- 화면 계산, 수식, Excel 다운로드의 재현성이 중요해졌다.
- Cafe24 응답 누락, 지연, 실패를 UX에서 처리해야 한다.
- 과거 기간 조회 결과를 동일하게 다시 설명할 수 있어야 한다.

현재 결론은 다음과 같다.

> DB 도입은 늦지 않았다. 오히려 지금이 적절한 시점이다.
> 단, 처음부터 DB를 모든 업무 원장으로 만들지 말고, Cafe24 스냅샷/캐시 + 사용자 설정 저장소로 시작해야 한다.

## 2. 핵심 원칙

### 2.1 Cafe24는 당분간 원천 데이터다

Cafe24 주문, 상품, 옵션, 판매 데이터는 당분간 원천 데이터로 유지한다.

DB 도입이 Cafe24를 즉시 대체한다는 뜻은 아니다. DB는 먼저 조회 재현성, 장애 완충, 사용자 설정 저장을 담당한다.

### 2.2 DB의 1차 역할은 캐시와 사용자 설정 저장소다

1단계 DB 역할은 다음으로 제한한다.

- Cafe24 원본 응답 스냅샷 저장
- 조회 기간별 판매 데이터 캐시
- 상품/옵션 메타데이터 캐시
- 사용자 정의 매핑 규칙 저장
- 세트상품 구성 override 저장
- Catchup 전용 세트상품 정의 저장
- 계산 결과 재현을 위한 기준 버전 저장

이 단계에서는 DB를 "업무 원장"으로 과도하게 확장하지 않는다.

### 2.3 세트상품 정의는 Cafe24 원천 데이터가 아니다

세트상품 구성 정의는 Cafe24에 존재하지 않고 Catchup 화면과 계산에서만 의미를 가진다.

예를 들어 세트상품 구성 편집 화면의 다음 정보는 Cafe24에서 가져오는 원본 데이터가 아니라 Catchup의 업무 정의다.

- 세트상품 코드와 옵션별 구성 그룹
- 공통 구성
- 선택 옵션 구성
- 구성 L상품/옵션
- 구성 수량
- 세트가
- 구성 합계
- 삭제/추가/변경된 사용자 정의 구성

따라서 세트상품 정의는 단순 Cafe24 응답 캐시가 아니라 DB 원천 데이터로 다루는 것이 맞다.

세트상품의 개별 상품명, 옵션명, 가격 후보 같은 참조 정보는 Cafe24 상품/옵션 메타데이터에서 가져올 수 있다. 하지만 "이 세트상품 옵션은 어떤 L상품/옵션 몇 개로 구성된다"는 관계 자체는 Catchup DB가 원천이어야 한다.

정리하면 다음과 같다.

| 데이터 | 원천 |
| --- | --- |
| Cafe24 상품 코드, 상품명, 옵션명 | Cafe24 |
| Cafe24 주문/판매 수량 | Cafe24 |
| L상품 단가 후보 | Cafe24 우선, 필요 시 DB 보정 |
| 세트상품 구성 관계 | Catchup DB |
| 세트상품 구성 수량 | Catchup DB |
| 세트상품 구성 세트가 | Catchup DB |
| 세트상품 구성 변경 이력 | Catchup DB |

### 2.4 DB와 Cafe24의 책임을 섞지 않는다

각 데이터는 다음 중 하나로 명확히 분류되어야 한다.

- Cafe24 원천 데이터
- DB 원천 데이터
- DB 캐시 데이터
- 계산 파생 데이터
- 사용자 설정 데이터

이 분류가 없으면 화면, Excel, 재조회 결과가 서로 다른 기준으로 계산될 위험이 있다.

## 3. 왜 지금 DB가 필요한가

### 3.1 재현성

사용자가 같은 기간을 다시 조회했을 때 계산 근거가 설명 가능해야 한다. Cafe24 응답이 바뀌거나 누락되면 과거 화면과 Excel 결과를 재현하기 어렵다.

### 3.2 장애 완충

Cafe24 API가 느리거나 실패해도, 최근 성공 스냅샷이나 캐시를 통해 사용자가 현재 상태를 이해할 수 있어야 한다.

### 3.3 사용자 변경사항 저장

매핑 규칙, 세트상품 구성 변경, 화면 설정, 수식 참조 정책 같은 사용자 변경사항은 Cafe24에 저장할 수 없다. 이 데이터는 DB 원천 데이터로 관리해야 한다.

### 3.4 검증 가능성

DB가 없으면 E2E 테스트가 외부 API 상태에 크게 의존한다. 스냅샷과 설정 저장소가 있으면 정상/비정상/복구 흐름을 더 안정적으로 검증할 수 있다.

## 4. 도입 시 주의점

DB 도입은 단순한 저장소 추가가 아니다. 다음 리스크를 먼저 설계해야 한다.

- Cafe24 최신값과 DB 저장값의 차이를 사용자에게 어떻게 설명할 것인가?
- 캐시 만료 시점은 언제인가?
- 사용자가 "새로고침"을 누르면 무엇이 갱신되는가?
- 조회 기간별 스냅샷은 얼마나 보관하는가?
- 매핑 규칙과 세트상품 구성 변경은 이력 관리가 필요한가?
- Excel 다운로드는 조회 당시 DB 스냅샷 기준인가, 최신 Cafe24 기준인가?
- 장애 시 사용자는 이전 데이터, 부분 데이터, 오류 중 무엇을 보아야 하는가?
- 마이그레이션과 백업 정책은 어떻게 할 것인가?

## 5. 권장 전환 단계

### Phase 0: 현재 구조 문서화

- Cafe24에서 직접 가져오는 데이터 목록 정리
- 화면 계산에 쓰이는 파생 데이터 목록 정리
- 사용자 변경사항 목록 정리
- Excel 다운로드가 참조하는 계산 기준 정리

### Phase 1: DB 책임 경계 설계

- Cafe24 원천 데이터와 DB 원천 데이터 구분
- 캐시 테이블과 설정 테이블 구분
- 조회 기간, 기준 시각, 계산 버전 모델 정의
- 장애/부분 응답/재시도 UX 정의

### Phase 2: 최소 DB 도입

- Catchup 전용 세트상품 정의 저장
- 사용자 매핑 규칙 저장
- 상품/옵션 메타데이터 캐시
- 기간별 판매 조회 스냅샷
- 사용자 화면/조회 설정 저장

### Phase 3: 계산 재현성 고도화

- 화면 계산 결과와 Excel 다운로드가 같은 스냅샷/설정 버전을 참조하도록 정리
- 계산 버전, 설정 버전, Cafe24 응답 버전을 추적
- 과거 조회 결과 재현 테스트 추가

### Phase 4: 운영 안정화

- 백업/복구
- 마이그레이션
- 동기화 실패 알림
- 캐시 정리 정책
- 관리자용 상태 확인 UI 또는 API

## 7. 현재 임시 결론

- DB 도입은 필요하다.
- 지금 바로 구현보다 설계 문서가 먼저다.
- 첫 DB는 "업무 원장"이 아니라 "Cafe24 스냅샷/캐시 + 사용자 설정 저장소"로 시작한다.
- 사용자 변경사항과 Cafe24 원천 데이터의 책임을 반드시 분리한다.
- 이후 구현은 작은 단계로 나눈다.

## 8. DB 저장 대상 분석

### 8.1 반드시 DB에 저장해야 하는 데이터

이 그룹은 Cafe24에 존재하지 않거나, Catchup만의 업무 판단이므로 DB 원천 데이터로 저장해야 한다.

#### 세트상품 정의

현재 코드의 `SET_PRODUCT_CONFIGS`에 해당한다.

- 세트상품 코드
- 세트상품명
- 세트상품 옵션 코드
- 세트상품 옵션명
- 공통 구성 여부
- 옵션별 구성 여부
- 구성 L상품 코드
- 구성 L상품 옵션 코드
- 구성 수량
- 세트가
- 구성 정렬 순서
- 사용 여부
- 삭제 여부
- 변경 이력

판단:

> 세트상품 정의는 DB 도입 1순위다.

이유:

- Cafe24에는 이 관계가 없다.
- 화면 계산과 Excel 매출 수식의 핵심 근거다.
- 현재는 코드에 하드코딩되어 있어 운영 중 수정/이력/검증이 어렵다.

#### 전환상품과 L상품 매핑 규칙

현재 코드의 `RULES`, `LuRuleOverride`, `setLuOverrides`에 해당한다.

- U상품 코드
- U상품 옵션 코드
- L상품 코드
- L상품 옵션 코드
- 매핑 비율
- 기본 규칙 여부
- 사용자 override 여부
- 활성/비활성 상태
- 생성/수정자
- 적용 시작일
- 적용 종료일
- 변경 이력

판단:

> 매핑 규칙도 DB 원천 데이터다.

이유:

- Cafe24에는 U상품과 L상품의 집계 관계가 없다.
- 매출/수량 계산의 핵심 업무 규칙이다.
- 현재 화면에서 변경/해제되는 값은 브라우저 상태에 머물면 안 된다.

#### 사용자 정의 세트상품 변경사항

현재 코드의 `setComponentDrafts`, `setAddedComponents`에 해당한다.

- 구성 추가
- 구성 삭제
- 구성 L상품 변경
- 구성 옵션 변경
- 수량 변경
- 세트가 변경
- 임시 초안 여부
- 적용 완료 여부
- 변경 이력

판단:

> 세트상품 구성 변경은 세트상품 정의와 같은 DB 도메인으로 관리하되, 초안과 적용 완료를 구분해야 한다.

이유:

- 사용자가 편집한 내용은 Cafe24에 저장되지 않는다.
- 적용 전 초안과 적용 후 기준을 구분하지 않으면 계산 결과를 재현할 수 없다.

#### 사용자 설정

현재 코드의 `localStorage` 및 `useSettings`에 해당한다.

- 기본 조회 시작일/종료일
- 보기 모드
- 카테고리 표시 순서
- 카테고리 체크 상태
- 상품코드 화면 보기 폭 설정
- 향후 개인별 UI 설정

판단:

> 사용자별 설정은 DB 저장 대상이지만, 핵심 업무 데이터보다 우선순위는 낮다.

이유:

- 현재 localStorage는 브라우저별로 분리되어 운영 일관성이 낮다.
- 다만 계산 정합성의 핵심은 아니므로 Phase 2 후반 또는 Phase 3로 미룰 수 있다.

### 8.2 DB에 캐시로 저장해야 하는 데이터

이 그룹은 Cafe24가 원천이지만, 성능/재현성/장애 대응을 위해 DB에 저장한다.

#### Cafe24 상품/옵션 메타데이터

- 상품 코드
- 상품명
- 옵션 코드
- 옵션명
- 상품가
- 옵션가
- 판매 상태
- 카테고리
- Cafe24 원본 응답
- 마지막 동기화 시각
- 데이터 상태: loaded/missing/partial/error

판단:

> 상품/옵션 메타데이터는 DB 캐시다. 원천은 Cafe24다.

주의:

- Catchup에서 이름이나 가격을 보정할 수 있다면, Cafe24 캐시와 Catchup 보정값을 분리해야 한다.

#### 기간별 주문/판매 스냅샷

현재 `products-report` API와 집계 결과에 해당한다.

- 조회 시작일
- 조회 종료일
- 요청 시각
- Cafe24 주문 원본 응답 또는 정규화 주문 라인
- 상품별 직접판매 수량
- 옵션별 직접판매 수량
- 클레임/취소/반품 반영 값
- Cafe24 응답 누락 여부
- 집계 상태
- 재조회 가능 여부

판단:

> 기간별 판매 데이터는 DB 캐시이자 조회 스냅샷이다. 원천은 Cafe24지만, 화면/Excel 재현을 위해 저장해야 한다.

주의:

- 같은 기간을 다시 조회했을 때 기존 스냅샷을 덮어쓸지, 새 스냅샷 버전으로 남길지 설계해야 한다.

#### Cafe24 원본 응답

- categories 응답
- products 응답
- orders 응답
- 호출 URL
- 파라미터
- 응답 상태
- 응답 본문
- 에러 본문
- 호출 시각

판단:

> 원본 응답 저장은 디버깅과 재현성에 매우 유용하지만, 저장량이 커질 수 있으므로 보관 정책이 필요하다.

### 8.3 DB에 파생 결과로 저장할지 검토할 데이터

이 그룹은 원천 데이터와 규칙으로 다시 계산할 수 있다. 기본은 저장하지 않고 계산하되, 재현성과 성능이 필요하면 스냅샷으로 저장한다.

#### 화면 계산 결과

- 교차셀 수량
- 총판매
- 매출
- 합계행
- 카테고리 합계
- 전체 합계
- 수식 설명 모델

판단:

> 계산 결과는 기본적으로 파생 데이터다. DB 원천으로 만들면 안 된다.

다만 다음 목적이면 저장할 수 있다.

- 특정 조회 결과를 감사/재현해야 한다.
- Excel 다운로드 결과와 화면 결과를 완전히 고정해야 한다.
- Cafe24 또는 설정 변경 이후에도 과거 결과를 그대로 열어야 한다.

이 경우에도 `calculation_snapshot`으로 저장해야 하며, 원천 데이터처럼 수정하면 안 된다.

#### Excel 다운로드 결과

- 생성 파일 자체
- 생성 시각
- 사용한 조회 스냅샷 ID
- 사용한 설정 버전
- 사용한 계산 버전

판단:

> Excel 파일은 매번 생성해도 되지만, 업무 감사/재다운로드가 필요하면 파일 또는 생성 메타데이터를 저장한다.

### 8.4 DB에 저장하지 않는 것이 나은 데이터

다음은 DB에 원천으로 저장하지 않는 것이 좋다.

- 현재 hover 셀
- 현재 선택 셀
- 임시 모달 위치
- 임시 스크롤 위치
- 일시적인 로딩 상태
- 계산 중간값 중 원천으로 재구성 가능한 값
- Cafe24 최신 데이터와 구분되지 않는 임의 수정값

판단:

> UI 일시 상태는 DB가 아니라 브라우저 상태로 둔다. 필요하면 localStorage 정도로 충분하다.

## 9. 논의 로그

### 2026-06-26

- 사용자 의견:
  - 현재 구현은 DB 없이 모든 것을 Cafe24에서 받아오는 구조로 동작하고 있다.
  - DB를 도입해야 이에 적합한 아키텍처를 정의해야 할 시점이 되었다고 판단했다.
  - 늦었는지 질문했다.
- 판단:
  - 늦지 않았다.
  - 오히려 매핑, 세트상품 구성, 사용자 변경사항, 계산 재현성이 생긴 지금이 적절하다.
  - 단, DB를 처음부터 업무 원장으로 두면 위험하다.
- 결정:
  - DB 도입 논의를 계속 업데이트할 별도 문서로 관리한다.
  - 일정 시점에 사용자가 요청하면 git에 커밋한다.

#### 세트상품 정의에 대한 추가 논의

- 사용자 의견:
  - Cafe24에서 많은 데이터를 가져오는 것은 맞다.
  - 하지만 세트상품에 대한 정의는 Cafe24에는 존재하지 않고 오로지 Catchup에만 존재한다.
  - 따라서 세트상품 정의는 DB에 기록해야 할 부분이라고 판단된다.
- 판단:
  - 동의한다.
  - 세트상품 구성 관계, 구성 수량, 세트가는 Cafe24 캐시가 아니라 Catchup 업무 원천 데이터다.
  - Cafe24는 구성품 후보의 상품/옵션 메타데이터를 제공할 수 있지만, 세트 구성이라는 관계 자체는 제공하지 않는다.
- 결정:
  - DB 도입 1단계 범위에 "Catchup 전용 세트상품 정의 저장"을 포함한다.
  - 향후 설계에서 세트상품 정의의 버전, 적용 기간, 변경 이력, 기존 하드코딩 데이터 마이그레이션 방식을 반드시 다룬다.

#### DB 설계 요청

- 사용자 의견:
  - Catchup에 필요한 DB 설계를 기본부터 다시 확인해 달라고 요청했다.
  - 단순 아이디어가 아니라 현재 코드 구조와 업무 의미를 확인한 설계가 필요하다.
- 확인한 현재 구조:
  - `ProductCodesView.tsx`의 `SET_PRODUCT_CONFIGS`가 세트상품 구성 정의를 프론트 코드 상수로 보유한다.
  - `ProductCodesView.tsx`와 `ExcelOrderView.tsx`의 `RULES`가 U상품과 L상품의 매핑 규칙을 프론트 코드 상수로 보유한다.
  - 세트상품 구성 편집 초안은 React state에만 존재하며, 영속 저장되지 않는다.
  - 매핑 변경 override도 React state에만 존재하며, 영속 저장되지 않는다.
  - 화면 기간/보기 설정은 localStorage에 저장되어 브라우저별로 분리된다.
  - `/api/products-report-requests`는 조회 요청을 백엔드 메모리에 10분만 보관한다.
  - Cafe24 상품/주문 응답과 집계 결과는 DB에 저장되지 않는다.
- 판단:
  - DB 도입의 1차 목적은 Cafe24를 대체하는 것이 아니라 Catchup 고유 업무 정의를 원천화하고, Cafe24 조회 결과를 재현 가능한 스냅샷으로 보존하는 것이다.
  - 세트상품 구성과 U/L 매핑은 코드 상수에서 DB 원천 데이터로 이동해야 한다.
  - Cafe24 상품/옵션/주문은 원천은 Cafe24로 유지하되, 캐시와 조회 스냅샷으로 저장해야 한다.
- 산출물:
  - 상세 설계는 `docs/db-architecture-design.md`에 작성한다.

#### DB 설계 감리 결과

- 감리 요청:
  - DB 설계와 이를 감리하는 에이전트를 통해 설계 타당성을 검증한다.
- 감리 판정:
  - 초안은 FAIL.
  - Cafe24 원천과 Catchup 원천을 분리하는 방향은 타당하지만, 세트상품/매핑만 DB화하면 핵심 업무 기준이 여전히 프론트 상수에 남는다는 지적이다.
- 핵심 지적:
  - `SET_PRODUCT_CONFIGS`, `RULES` 외에도 `L_GROUPS`, `L_PRODUCT_DISPLAY_BY_CODE`, `QUERY_CODES`, `U_BLOCKS`, `EXCLUDED_U_PRODUCTS`가 DB 원천화 대상이다.
  - 조회 snapshot은 세트 정의/매핑/표시 기준/계산 정책을 불변 버전 FK로 참조해야 한다.
  - Excel 재현성을 선택 사항으로 두면 안 된다.
  - Cafe24 API 호출별 상태, 상품별 found/missing/failed/partial 상태, raw response 저장이 필요하다.
  - `aggregate()`의 취소/반품 제외, claim 차감, 가격 결정, 옵션 정규화 정책도 버전 관리해야 한다.
- 반영 결정:
  - `docs/db-architecture-design.md`를 감리 결과 기준으로 수정한다.
  - `docs/catchup-architecture-design.md`에도 상품코드 기준 세트, 계산 정책 버전, 계산/Excel snapshot을 아키텍처 핵심 요소로 반영한다.

#### 커밋 전 완성도 보완

- 사용자 질문:
  - 설계 문서가 커밋해도 될 수준인지 확인하고, 부족하면 완성하라고 요청했다.
- 보완한 항목:
  - 불변 기준 세트 변경 워크플로우를 정의했다.
  - 과거 조회 적용 정책을 "조회 생성 시점의 active 기준"으로 1차 확정했다.
  - snapshot/raw response/정규화 주문 라인/Excel metadata 보관 정책을 정의했다.
  - 전체 아키텍처 문서에도 기준 버전 운영 정책을 연결했다.
- 판단:
  - 1차 DB 도입 설계 기준으로 커밋 가능한 수준이다.
  - 사용자 계정/권한, PostgreSQL 전환, 장기 아카이브 저장소는 1차 구현의 blocker가 아니므로 보류 항목으로 둔다.
