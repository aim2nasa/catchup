# 하드왁스 판매/원가 집계 논리 구조 분석

작성일: 2026-05-23

## 목적

`상품출고&순이익(2026).xlsx`의 기존 하드왁스 집계 구조를 분석하고, 전산화 가능한 논리 구조로 재정의하기 위한 작업 노트다.

이 문서는 PRD/TRD/UI 설계 전에 업무 규칙과 데이터 구조를 명확히 기록하기 위한 중간 산출물이다. 이후 논의 내용은 이 문서에 계속 추가한다.

## 분석 대상

- 원본 파일: `docs/상품출고&순이익(2026).xlsx`
- 1차 분석 시트: `상품코드_4월 `
  - 실제 시트명 끝에 공백이 있음
- 1차 분석 범위: 1행~44행
- 비교 대상 웹 화면: `https://tars.giize.com/catchup/#hardwax`
- 참고 새 포맷 파일: `docs/상품출고&순이익(2026)_포맷1.xlsx`

## 분석 전제

엑셀의 데이터는 수작업으로 작성된 값이 많기 때문에, 셀 값 자체가 틀렸을 가능성을 항상 염두에 둔다.

따라서 엑셀은 정답 데이터가 아니라 다음을 파악하기 위한 참고 자료로 본다.

- 회사가 어떤 결과를 보고 싶어 했는지
- 어떤 업무 규칙이 암묵적으로 숨어 있는지
- 어떤 계산을 수작업으로 반복해왔는지
- 어떤 부분을 전산화하려고 했는지

숫자의 정확성은 cafe24 원천 데이터와 명시적인 정의표를 기준으로 다시 검증해야 한다.

## 용어 정의

### cafe24 상품

cafe24에는 `P00000HT` 같은 상품코드가 있다.

하나의 상품코드 아래에 여러 옵션이 있을 수 있고, 이 옵션은 상품품목코드로 식별된다. 같은 상품코드 안에서도 상품품목코드별 가격이 다를 수 있다.

논의 편의를 위해 앞으로 `상품코드`와 `상품품목코드`를 합쳐서 짧게 `상품`이라고 부른다.

### L

`L`은 엑셀 좌측 A열에 있는 회사 내부 기준 상품이다.

예:

- 라이코젯아이브로우500
- 라이코드림하이브리드500
- 비즈하이브리드800
- 핑키니하드

회사가 최종적으로 알고 싶은 것은 각 `L`이 몇 개 팔렸는지다.

`500g총합계`, `1kg총합계`는 L이 아니라 그룹 합계 행이다.

### U

`U`는 L을 다른 방식으로 판매한 특수 상품이다.

예:

- 인증/마스터
- 지사비즈4종
- 컵비즈묶음
- 컵비즈세트
- 묶음할인15%
- 할인+증정
- 스타터키트
- 비즈5KG행사
- 바디스타터키트

U는 다음과 같은 경우를 포함한다.

- L을 조합해서 세트로 구성한 상품
- L을 묶음/할인 조건으로 판매한 상품
- 특정 업체에게만 제공한 상품
- 행사 또는 증정이 포함된 상품

즉 U도 cafe24에서는 상품코드/상품품목코드를 가진 정상 상품이지만, 회사 내부 집계에서는 하나 이상의 L로 환산되어야 한다.

## 기존 엑셀의 의도

기존 엑셀은 L별 판매수량, 매출, 원가를 계산하기 위한 문서다.

원천 판매 데이터는 cafe24에서 가져온다. 현재 웹 하드왁스 화면은 cafe24에서 가져온 원천 데이터의 상품코드, 상품품목코드, 단가, 판매수, 매출을 보여준다.

엑셀은 이 cafe24 원천 데이터를 회사 내부 기준인 L별 집계표로 옮긴 결과다.

## 기존 엑셀의 구조

원본 `상품코드_4월 ` 시트 1~44행 기준으로는 다음과 같이 볼 수 있다.

- A:B열: L 상품명 / cafe24 상품코드 또는 상품코드 묶음
- C:I열: 판매수량 입력/집계 영역
- J열: 품목별 총 판매수량
- K:Q열: 판매유형별 매출 환산 영역
- R열: 품목별 매출 합계
- S열: 원가 합계

행 구조:

- 1~6행: 헤더 겸 U 상품코드/설명
- 7~23행: 500g 하드왁스 품목
- 24행: 500g 총합계
- 25~28행: 컵비즈왁스 옵션 품목
- 29~43행: 1kg 하드왁스 품목
- 44행: 1kg 총합계

## 기존 엑셀에서 확인된 문제

### 1. U 판매단가가 수식 안에 하드코딩되어 있음

예:

```text
O7 = F7 * 21040
```

여기서 `21040`은 어느 U 상품인지는 명확하지 않지만, 해당 상품이 21,040원으로 팔렸다는 의미다.

M~S열의 계산을 보면 상품마다 서로 다른 값이 적용되어 있다. 즉 판매단가가 별도의 기준표에 있는 것이 아니라 셀 수식 안에 숫자로 박혀 있다.

### 2. L 원가가 수식 안에 하드코딩되어 있음

S열은 상품별 원가를 계산한다.

예:

```text
S7 = (C7+D7+E7+F7+I7+H7+G7) * 8655
```

여기서 `8655`는 해당 L의 단위 원가로 보인다. 하지만 이 값도 별도의 원가 마스터가 아니라 수식 안에 박혀 있다.

### 3. U와 L의 관계 정의가 없음

U 상품이 어떤 L 상품과 어떤 관계를 갖는지 정의한 표가 없다.

예를 들어 U가 다음과 같은 세트 상품일 수 있다.

```text
U 상품 1개 = P00000HT 1개 + P00000XE 3개
```

하지만 기존 엑셀에는 이 관계가 명시되어 있지 않다. 셀 위치와 수작업 입력을 통해 사람이 해석해야 한다.

### 4. cafe24 상품코드/상품품목코드가 명확히 드러나지 않음

U도 cafe24에서는 상품코드/상품품목코드를 가진 상품이다. 그러나 기존 엑셀에서는 E, F, G열 등에서 어떤 코드/품목코드로 팔린 것인지 뭉뚱그려져 있다.

이 때문에 전산화해서 자동 집계하기 어렵다.

### 5. 상품코드 묶음이 병합 셀에 들어 있음

예: 원본 시트의 `B13:B21` 영역에는 다음 코드들이 하나의 병합 셀에 들어 있다.

```text
P0000BIF / P0000BLD / P0000BMJ / P0000BMI / P0000BMY
```

이 구조에서는 각 L 행이 어떤 cafe24 상품/상품품목코드와 연결되는지 명확히 알기 어렵다.

## 새 포맷의 방향

사용자가 기존 엑셀의 문제를 분석한 뒤 새 포맷을 정의했다.

새 포맷의 핵심은 다음과 같다.

- 행 = L
- 열 = L 직접판매 또는 U
- 교차 셀 = 해당 U가 팔렸을 때 실제로 어떤 L로 몇 개 환산되는지
  - 이 문서에서는 `교차 셀`을 `LU셀`이라고 부른다.
- 오른쪽 합계 = 직접판매 + U 배분을 합친 L별 최종 판매수/매출

> **LU셀(교차점) 판정**  
> LU셀은 `L 행/옵션`과 `U 행/옵션`의 교차점에서 LU매핑이 정의된 경우에만 성립한다.  
> 즉, 해당 조합에 LU매핑이 있으면 LU셀이다.  
> LU매핑이 있더라도 수량이 0이면 값은 0이지만, LU셀 자체는 유지한다.

즉 기존에 수식과 셀 위치에 숨어 있던 규칙을 명시적인 교차표로 꺼낸 것이다.

## D열과 E열 이후의 의미

새 포맷에서:

- D열: L이 자기 상품코드로 직접 팔린 수량
- E열 이후: U로 팔렸지만 실제로는 어떤 L이 몇 개 팔린 것인지 배분한 수량

예:

```text
cafe24에서 U 상품이 1개 팔림
U-L 관계표에 따라 L-A 1개, L-B 3개로 환산
각 L 행의 해당 U 열에 환산 수량 표시
```

## 개선된 논리 구조

전산화 가능한 구조로 만들 때 L/U 자체의 상품 정의표는 별도로 만들지 않는 방향이 더 적절하다.

cafe24 API에서 상품코드/상품품목코드를 기준으로 상품명과 단가를 가져올 수 있기 때문이다. 따라서 상품명/판매가를 중복 관리하는 L/U 정의표는 불필요하다.

별도로 필요한 것은 cafe24에 없는 내부 업무 정보다.

### 1. L 원가표

L의 단위 원가를 관리한다. cafe24는 판매가를 제공하지만 회사 내부 원가는 제공하지 않으므로 별도 관리가 필요하다.

필드 후보:

- cafe24 상품코드
- cafe24 상품품목코드
- 그룹: 500g, 800g, 1kg, 5kg, 컵비즈 등
- 내부 표시명 (선택)
- 단위 원가
- 적용 시작일/종료일
- 표시 순서
- 비고

### 2. U-L 관계표

U가 팔렸을 때 어떤 L로 몇 개 환산되는지 정의한다.

이 표가 기존 엑셀에서 가장 크게 빠져 있던 정보다.

필드 후보:

- U cafe24 상품코드
- U cafe24 상품품목코드
- L cafe24 상품코드
- L cafe24 상품품목코드
- 환산 수량
- 적용 시작일/종료일
- 관계 유형: 세트, 할인, 업체전용, 행사, 증정 등
- 비고

예:

```text
U 상품 1개 -> L 상품 A 1개
U 상품 1개 -> L 상품 B 3개
```

박스/묶음 상품도 같은 방식으로 처리한다.

예:

```text
U 상품명: 선샤인 비즈왁스 800g 1박스 18개
U 판매수: 4
U-L 환산수량: 18
L 판매수: 4 * 18 = 72
```

따라서 이 프로젝트에서 말하는 `판매수`는 단순히 cafe24 주문 라인의 판매수량이 아니라, 회사 내부 기준 L로 환산된 실제 L 판매수량이다.

### 중요 예시: P0000BMJ -> P0000BMI

`P0000BMJ`는 cafe24 상품명상 `선샤인 비즈왁스 800g (1박스 18개)` 상품이다.

이 상품이 2026년 4월에 4개 판매되었다면, 회사 내부 기준 L 판매수량은 `4`가 아니라 `72`로 봐야 한다.

LU 매핑표에는 다음처럼 정의한다.

| U 상품코드 | U 상품품목코드 | U 의미 | L 상품코드 | L 상품품목코드 | L 의미 | 환산수량 |
|---|---|---|---|---|---|---:|
| P0000BMJ | P0000BMJ000A | 선샤인 비즈왁스 800g 1박스 18개 | P0000BMI | - | 선샤인비즈왁스800 | 18 |

계산:

```text
cafe24 U 판매수 4 * 환산수량 18 = L 판매수 72
```

이 예시는 LU 매핑표에서 `환산수량`이 왜 필요한지 보여주는 대표 사례다.

### LU 매핑표 관리 방식

LU 매핑은 내부적으로는 하나의 관계 구조로 저장할 수 있다.

하지만 운영자가 관리할 때는 경우별로 나누어 보는 것이 맞다. 매핑 유형마다 해석 방식과 검토 포인트가 다르기 때문이다.

권장 관리 유형:

| 유형 | 의미 | 예시 | 주요 확인점 |
|---|---|---|---|
| 1:1 옵션 매핑 | U 상품품목 하나가 L 하나로 대응 | `P0000BLR000S -> P0000BIF / CN` | 옵션명과 L명이 정확히 대응되는지 |
| 세트 구성 매핑 | U 하나가 여러 L로 분해 | 세트상품 1개 = `P00000HT` 1개 + `P00000XE` 3개 | 구성품과 구성 수량 |
| 박스/묶음 환산 매핑 | U 하나가 L 여러 개로 환산 | `P0000BMJ -> P0000BMI`, 환산수량 18 | 박스/묶음 구성 수량 |
| 행사/증정 매핑 | 행사 또는 증정이 포함된 U를 L로 해석 | 할인+증정 상품 | 판매수/매출/원가 반영 기준 |
| 미확정/검토 필요 | L 대응이 아직 확정되지 않은 U | `P007000ZC` | 상품 카탈로그 API 조회 및 업무 판단 |

추천 원칙:

- 저장 구조는 통합된 `LU 매핑표` 하나로 둔다.
- 각 매핑에는 `매핑유형` 필드를 둔다.
- UI나 운영용 표에서는 매핑유형별로 나누어 보여준다.
- 미확정 매핑은 별도 상태로 관리해서 집계 누락이나 잘못된 수기 배분을 막는다.

### 상품품목코드 표시값과 내부 키

단일 품목 상품은 cafe24 관리자 판매분석 화면에서 상품품목코드가 `-`로 표시된다.

하지만 API 내부에서는 이런 상품도 실제 `variant_code`를 가진다.

예:

| 상품코드 | 엑셀/화면 표시 품목코드 | API 내부 variant_code | 비고 |
|---|---|---|---|
| P00000YS | - | P00000YS000A | 단일 품목 |
| P00000YU | - | P00000YU000B | 단일 품목 |

운영 원칙:

- 엑셀과 사용자 화면에는 cafe24 관리자 화면과 맞춰 `-`로 표시한다.
- 시스템 내부 저장/매칭에는 실제 `variant_code`를 사용한다.
- LU 매핑표도 표시용 품목코드와 내부 variant_code를 분리해서 생각한다.

이 지점은 미묘하지만 중요하다. 표시값 `-`만 저장하면 API 주문/상품 데이터와 정확히 조인하기 어렵고, 반대로 사용자 화면에 `P00000YS000A`만 노출하면 cafe24 관리자 화면과 달라져 운영자가 혼란스러울 수 있다.

예시 통합 구조:

| 매핑유형 | U 상품코드 | U 상품품목코드 | L 상품코드 | L 상품품목코드 | 환산수량 | 상태 | 비고 |
|---|---|---|---|---|---:|---|---|
| 1:1 옵션 | P0000BLR | P0000BLR000S | P0000BIF | CN | 1 | 확정 | 옵션명 기준 |
| 세트 구성 | U_SET001 | U_SET001000A | P00000HT | - | 1 | 확정 | 구성품 |
| 세트 구성 | U_SET001 | U_SET001000A | P00000XE | - | 3 | 확정 | 구성품 |
| 박스환산 | P0000BMJ | P0000BMJ000A | P0000BMI | - | 18 | 확정 | 1박스 18개 |
| 미확정 | P007000ZC | - | - | - | - | 검토필요 | 카탈로그 API 조회 필요 |

### 3. cafe24 판매내역

cafe24에서 가져온 원천 판매 데이터를 저장하거나 조회한다.

필드 후보:

- 주문일
- 상품코드
- 상품품목코드
- cafe24 상품명
- 옵션명
- 판매수량
- 단가
- 매출
- 주문 상태
- 취소/반품/클레임 수량

### 4. L별 집계 결과

최종 보고서용 결과다.

필드 후보:

- 기간
- L ID
- L 이름
- 직접 판매수량
- U 경유 판매수량
- 총 판매수량
- 매출
- 원가
- 순이익

## 계산 흐름

목표 계산 흐름:

```text
cafe24 판매내역
-> 상품이 L인지 U인지 판별
-> L이면 직접 집계
-> U이면 U-L 관계표에 따라 L 수량으로 환산
-> L별 판매수량/매출/원가 계산
```

직접판매와 U 판매 모두 원천은 cafe24다. 차이는 해석 방식이다.

- L 직접판매: cafe24 판매수량을 그대로 L에 더함
- U 판매: cafe24 판매수량을 가져온 뒤 U-L 매핑에 따라 L 수량으로 환산해서 더함
- 박스/묶음 U 판매: cafe24 판매수량에 U-L 관계표의 환산 수량을 곱해서 L 수량으로 더함

## 기대 효과

위 표들이 정의되면 기존 엑셀에 박혀 있는 하드코딩 숫자를 제거할 수 있다.

기존:

```text
O7 = F7 * 21040
S7 = 판매수량합계 * 8655
```

개선:

```text
매출 = cafe24 판매수량 * U 또는 L 상품 마스터의 판매가
원가 = L별 환산 판매수량 * L 상품 마스터의 단위 원가
```

즉 cafe24 값을 읽어오는 즉시 엑셀과 같은 계산을 자동으로 수행할 수 있다.

## 현재까지 확정된 핵심 결론

- 기존 엑셀은 업무 의도는 있으나, 전산화하기에는 하드코딩과 암묵 규칙이 많다.
- 회사가 보고 싶은 기준은 cafe24 상품 자체가 아니라 L별 판매수량/매출/원가다.
- U는 cafe24에서 판매되는 별도 상품이지만, 내부 집계에서는 L로 환산되어야 한다.
- L/U 상품명과 판매가는 cafe24 API에서 가져올 수 있으므로 별도 상품 정의표는 만들지 않는다.
- 전산화의 핵심은 L 원가와 U-L 관계를 명시적인 표로 분리하는 것이다.
- 화면은 교차표 형태로 보여줄 수 있지만, 내부 데이터 구조는 행 단위 관계표가 더 적합하다.

## 다음 확인 필요 항목

- L의 단위 원가는 월별로 바뀌는지, 상품별 고정인지
- U 판매가는 cafe24 판매가를 그대로 신뢰할지, 별도 기준가를 관리해야 하는지
- U-L 관계가 기간별로 바뀔 수 있는지
- 증정 상품은 판매수량에는 포함하고 매출에는 0으로 볼지
- 순이익 계산 범위가 원가까지만인지, 배송비/수수료/기타 비용까지 포함하는지
- 컵비즈 25~28행처럼 수량 합계와 매출 합계의 포함 범위가 다른 부분이 의도인지
