# PRD/TRD/UI 설계 프롬프트 초안

## 배경 요약

캐치업코리아는 cafe24 기반 쇼핑몰의 판매 데이터를 엑셀로 집계하고 있다.

현재 엑셀은 상품별 판매수, 매출, 원가, 이익을 계산하기 위한 업무 문서지만, 많은 의미가 셀 위치와 수식 안에 숨어 있다. 특히 cafe24 상품코드/상품품목코드와 내부 집계 기준 상품의 관계가 명시되어 있지 않아, 전산화가 어렵다.

이 엑셀은 전산화 대상 화면을 그대로 정의하는 문서가 아니다. 엑셀은 기존 업무를 이해하기 위한 참고 데이터이며, 실제 시스템은 사용자가 더 쉽게 이해하고 검증할 수 있는 구조로 재설계해야 한다.

이번 분석에서는 하드왁스 `상품코드_4월-NEW1` 시트를 기준으로, cafe24 판매 데이터와 엑셀 수량을 대조했다.

핵심 용어:

- `L`: 회사가 최종적으로 판매수, 원가, 이익을 집계하고 싶은 기준 상품
- `U`: cafe24에서 별도 상품으로 팔리지만, 내부 집계에서는 L로 옮겨야 하는 상품
- `LU 매핑`: U 상품품목이 어떤 L 상품품목으로 반영되는지 정의한 관계
- `LU셀`: 엑셀 교차표에서 U와 L의 교차점에 적힌 환산 수량(1개 U에서 반영되는 L 수량)

2026년 4월 하드왁스 검증 범위에서는 `P00000YU / -`를 제외하면 U-L 관계가 1:1 매핑으로 설명된다.

## 요구사항 수용 프로세스

새로운 요구사항은 즉시 PRD/TRD/UI 설계나 구현에 섞지 않는다.

먼저 요구사항 인박스에 기록하고, 승인된 항목만 각 설계 문서로 승격한다.

참조 문서:

- 요구사항 수용 프로세스: `docs/requirements-to-design-process.md`
- 요구사항 인박스: `docs/requirement-intake.md`

기본 흐름:

```text
요구사항 발견
  -> 요구사항 인박스 기록
  -> PRD/TRD/UI/UX 후보 분류
  -> 승인
  -> 설계 문서 반영
  -> 구현 작업 분리
  -> 검증
```

PRD/TRD/UI 초안 작성 시에도 이 구조를 전제로 한다.

- PRD에는 승인된 제품 요구만 반영한다.
- TRD에는 구현 방식, 데이터 모델, API, 검증 방식이 필요한 요구만 반영한다.
- UI/UX 설계에는 사용자 흐름, 화면 구조, 이해 방식에 영향을 주는 요구만 반영한다.
- 인터뷰에서 확인이 필요한 내용은 바로 확정하지 않고 인터뷰 질문으로 둔다.

## PRD 작성 프롬프트 초안

아래 내용을 바탕으로 제품 요구사항 문서(PRD)를 작성해줘.

목표는 cafe24 판매 데이터를 읽어와 회사 내부 기준 상품(L)별 판매수, 매출, 원가, 이익을 자동 집계하는 시스템을 설계하는 것이다.

주의할 점:

- 기존 엑셀 화면을 그대로 웹 화면으로 복제하지 않는다.
- 엑셀은 업무 규칙을 추출하기 위한 참고자료로 사용한다.
- 최종 화면은 사용자가 수량, 매출, 원가, 매핑 상태를 쉽게 이해하고 검증할 수 있게 재구성한다.
- 복잡한 교차표보다 업무 질문에 바로 답하는 화면을 우선한다.

현재 문제:

- 기존 엑셀은 수식과 셀 위치에 업무 의미가 숨어 있다.
- cafe24 상품(U)과 내부 집계 상품(L)의 관계가 명시되어 있지 않다.
- U 상품의 판매수는 L 상품으로 옮겨야 하지만, 어떤 기준으로 옮기는지 표준화되어 있지 않다.
- 상품명과 판매가는 cafe24에서 조회할 수 있지만, L 상품 원가는 별도 관리가 필요하다.
- 일부 합계 행은 수량과 금액의 합산 범위가 일치하지 않는다.
- 단일 옵션 상품은 cafe24 관리자 화면에서 품목코드가 `-`로 보이지만, 내부적으로는 실제 variant_code가 존재한다.

핵심 요구사항:

- cafe24에서 상품, 상품품목, 판매수, 판매가, 매출 데이터를 조회한다.
- 내부 기준 상품인 L을 기준으로 판매수와 매출을 집계한다.
- U 상품품목을 L 상품품목으로 변환하는 LU 매핑표를 관리한다.
- LU 매핑 유형은 최소한 다음을 지원한다.
  - 1:1 매핑
  - 박스/묶음 환산 매핑
  - 세트 구성 매핑
  - 미확정 매핑
- L 상품별 원가표를 관리한다.
- 판매수, 매출, 원가, 이익을 월별로 계산한다.
- 미확정 매핑이 있으면 집계 결과에서 명확히 표시한다.
- 기존 엑셀과 비교할 수 있는 검증 화면을 제공한다.
- 엑셀과 같은 형태의 표를 그대로 보여주는 것이 아니라, 사용자가 이해하기 쉬운 집계/검증 화면을 제공한다.

중요한 업무 규칙:

- L/U 상품명과 판매가는 cafe24를 원천으로 사용한다.
- 내부 원가는 별도 L 원가표에서 관리한다.
- 화면 표시용 품목코드와 내부 variant_code는 분리한다.
- 단일 옵션 상품은 화면에는 `-`로 표시하되, 내부에서는 실제 variant_code로 조인한다.
- `P00000YU / -`처럼 L 매핑이 불명확한 U 판매는 임의로 배치하지 않고 확인 필요 상태로 둔다.

PRD에 포함할 항목:

- 제품 목적
- 사용자와 주요 사용 시나리오
- 현재 엑셀 업무의 문제점
- 핵심 개념 정의: L, U, LU 매핑, L 원가표
- 기능 요구사항
- 비기능 요구사항
- 데이터 검증 요구사항
- 예외 처리 정책
- MVP 범위
- MVP 이후 확장 범위
- 미확정 질문 목록
- 요구사항 인박스 운영 방식
- 요구사항이 PRD로 승격되는 기준

## TRD 작성 프롬프트 초안

아래 내용을 바탕으로 기술 요구사항 문서(TRD)를 작성해줘.

시스템은 cafe24 API와 연동하여 판매 데이터를 가져오고, 내부 LU 매핑과 L 원가표를 기준으로 월별 판매/원가/이익 집계를 계산한다.

현재 프로젝트는 FastAPI 백엔드와 React 프론트엔드 구조를 사용한다.

기술적으로 해결해야 할 핵심 문제:

- cafe24 catalog API와 sales/order API를 구분해서 사용해야 한다.
- 판매된 상품만 조회하는 API로는 품목코드 전체를 알 수 없다.
- 상품품목코드 검증은 반드시 catalog 조회를 기준으로 해야 한다.
- 주문/판매 데이터는 기간 조건으로 조회한다.
- 상품명, 판매가, 품목코드는 cafe24를 원천으로 한다.
- L 원가는 내부 DB에서 관리한다.
- LU 매핑은 내부 DB에서 관리한다.

제안 데이터 모델:

- cafe24_products
  - product_code
  - product_name
  - product_no
  - updated_at
- cafe24_variants
  - product_code
  - variant_code
  - display_variant_code
  - option_name
  - price
  - is_single_variant
- l_products
  - l_product_id
  - product_code
  - variant_code
  - display_name
  - active
- lu_mappings
  - mapping_id
  - mapping_type
  - u_product_code
  - u_variant_code
  - l_product_code
  - l_variant_code
  - quantity_multiplier
  - status
  - effective_from
  - effective_to
  - note
- l_costs
  - cost_id
  - l_product_code
  - l_variant_code
  - unit_cost
  - effective_from
  - effective_to
- sales_facts
  - sales_period
  - product_code
  - variant_code
  - quantity
  - revenue
  - source
- l_sales_results
  - sales_period
  - l_product_code
  - l_variant_code
  - direct_quantity
  - mapped_quantity
  - total_quantity
  - revenue
  - cost
  - profit

핵심 처리 흐름:

1. 기간을 입력받는다.
2. cafe24 catalog에서 대상 상품과 품목코드를 조회한다.
3. cafe24 sales/order 데이터에서 판매수와 매출을 조회한다.
4. L 직접판매는 L 상품 자체 판매수로 집계한다.
5. U 판매는 LU 매핑표를 통해 L 수량으로 변환한다.
6. 환산수량이 있으면 `U 판매수 × quantity_multiplier`로 계산한다.
7. L 원가표를 적용해 원가와 이익을 계산한다.
8. 미확정 매핑이 있으면 결과에 별도로 표시한다.
9. 기존 엑셀 형식과 비교 가능한 검증 데이터를 제공한다.

TRD에 포함할 항목:

- 시스템 아키텍처
- cafe24 API 연동 방식
- 데이터 모델
- 집계 알고리즘
- LU 매핑 처리 방식
- 원가 적용 방식
- 미확정 매핑 처리
- 검증/테스트 전략
- 에러 처리
- 캐싱 전략
- 향후 확장 고려사항
- 요구사항 변경이 데이터 모델/API/집계 로직에 반영되는 절차

특히 아래 정책을 명확히 써줘:

- catalog 조회와 sales 조회를 분리한다.
- 판매되지 않은 옵션도 LU 매핑 대상이 될 수 있으므로 catalog 기준으로 품목코드를 검증한다.
- 단일 옵션 상품의 화면 표시값 `-`와 내부 variant_code를 분리한다.
- 미확정 매핑은 자동 집계하지 않는다.
- 기존 엑셀의 수식은 참고자료일 뿐, 전산화 기준은 명시적 정의표를 따른다.
- 기존 엑셀 레이아웃을 데이터 모델이나 UI 구조로 그대로 옮기지 않는다.

## UI 설계 프롬프트 초안

아래 내용을 바탕으로 운영자가 사용할 웹 UI 설계안을 작성해줘.

이 UI는 cafe24 판매 데이터를 내부 기준 상품 L로 집계하고, LU 매핑과 원가를 관리하기 위한 업무용 도구다.

중요한 방향:

- 기존 엑셀은 참고 데이터일 뿐이다.
- 엑셀처럼 넓고 복잡한 교차표를 그대로 재현하지 않는다.
- 사용자가 “무엇이 얼마나 팔렸고, 어떤 U가 어떤 L로 반영됐고, 무엇이 아직 미확정인지”를 쉽게 파악하게 한다.
- 필요한 경우에만 상세 매핑 테이블로 내려갈 수 있게 한다.

디자인 방향:

- 업무용 운영 도구처럼 조용하고 명확해야 한다.
- 화려한 랜딩 페이지가 아니라 바로 사용할 수 있는 화면이어야 한다.
- 엑셀을 대체하거나 검증하는 도구이지만, 엑셀 레이아웃을 그대로 따라가면 안 된다.
- 표는 사용하되, 사용자가 이해하기 쉬운 요약 → 상세 구조로 설계한다.
- 운영자가 수량 차이, 미확정 매핑, 원가 누락을 빠르게 찾을 수 있어야 한다.

필요한 주요 화면:

### 1. 월별 집계 화면

목적:

- 기간을 선택하고 L 상품별 판매수, 매출, 원가, 이익을 확인한다.
- “이 달에 실제로 어떤 L 상품이 얼마나 팔렸는가?”에 바로 답한다.

필수 요소:

- 기간 선택
- 상품군 선택
- 집계 실행 버튼
- 주요 요약 카드
  - 총 판매수
  - 총 매출
  - 총 원가
  - 총 이익
  - 미확정 매핑 수
- L 상품별 결과 테이블
- 직접판매 수량
- U 매핑 수량
- 총 수량
- 매출
- 원가
- 이익
- 미확정 매핑 경고

표현 방식:

- 기본 화면은 L 기준 요약표로 보여준다.
- 사용자가 L 행을 펼치면 해당 L에 반영된 U 판매 내역을 보여준다.
- 처음부터 엑셀처럼 모든 U 열을 가로로 펼치지 않는다.

### 2. LU 매핑 관리 화면

목적:

- U 상품품목이 어떤 L 상품품목으로 들어가는지 관리한다.

필수 요소:

- U 상품 검색
- U 상품품목 목록
- L 상품 검색
- 매핑유형 선택
- 환산수량 입력
- 상태 선택: 확정, 검토필요, 미사용
- 적용 기간
- 저장/변경 이력

표현 방식:

- U 상품품목을 선택하면 현재 연결된 L을 보여준다.
- L 후보는 상품명/옵션명 유사도와 기존 매핑을 기준으로 추천할 수 있다.
- 1:1 매핑은 단순하게 보이고, 박스/세트 매핑만 별도 상세 입력을 제공한다.

매핑 유형:

- 1:1
- 박스/묶음 환산
- 세트 구성
- 미확정

### 3. 미확정 매핑 검토 화면

목적:

- cafe24 판매는 있었지만 L로 배치되지 않은 U 판매를 확인한다.

필수 요소:

- 기간
- U 상품코드
- U 상품품목코드
- 상품명/옵션명
- 판매수
- 매출
- 추천 L 후보
- 매핑 생성 버튼

표현 방식:

- 운영자가 가장 먼저 처리해야 할 문제 목록으로 보여준다.
- “이 판매수는 아직 L에 들어가지 않았다”는 점을 명확히 표시한다.
- 해결 버튼을 누르면 LU 매핑 생성 화면으로 이어진다.

예시:

- `P00000YU / -`
- 판매수 1
- L 매핑 미확정

### 4. L 원가 관리 화면

목적:

- L 상품별 원가를 관리한다.

필수 요소:

- L 상품 검색
- 상품코드
- 상품품목코드
- 상품명
- 단위 원가
- 적용 시작일
- 적용 종료일
- 변경 이력

### 5. cafe24 데이터 검증 화면

목적:

- cafe24 원천 판매수와 내부 집계 수량이 맞는지 확인한다.
- 엑셀과 똑같이 보여주는 화면이 아니라, 차이와 미확정 항목을 빠르게 찾는 화면이다.

필수 요소:

- U 옵션별 cafe24 판매수
- 해당 U가 반영된 L 수량
- 차이
- 상태: 정상, 불일치, 미확정
- 엑셀 다운로드

표현 방식:

- 기본은 상태별 요약을 보여준다.
- 정상 항목은 접어두고, 불일치/미확정 항목을 먼저 보여준다.
- 필요할 때만 U옵션별 상세 수량을 펼쳐본다.

UI 설계에 포함할 항목:

- 정보 구조
- 주요 화면별 목적
- 테이블 컬럼 설계
- 필터/검색/상태 표시
- 미확정 매핑 처리 UX
- 오류/경고 표시 방식
- 엑셀 검증 파일과 비교하는 방식
- 엑셀을 그대로 복제하지 않고 더 쉬운 화면으로 바꾸는 방식
- 새 UI 요구사항이 생겼을 때 인박스에 기록하고 UX 후보로 승격하는 절차

## MVP 범위 제안

MVP에서는 아래까지만 만든다.

1. cafe24 상품/품목 catalog 조회
2. cafe24 월별 판매수 조회
3. LU 매핑표 관리
4. L 원가표 관리
5. L 기준 월별 집계
6. 미확정 매핑 표시
7. 엑셀 검증용 다운로드

MVP UI 원칙:

- 첫 화면은 엑셀형 교차표가 아니라 월별 집계 요약이어야 한다.
- 미확정 매핑과 불일치 항목을 먼저 드러낸다.
- 상세 검증이 필요한 경우에만 U 옵션별 상세를 펼친다.
- 엑셀 다운로드는 보조 기능으로 둔다.

MVP에서 제외할 수 있는 것:

- 복잡한 권한 관리
- 회계 시스템 연동
- 재고 관리
- 자동 원가 추정
- 전체 상품군 확장

우선 하드왁스 2026년 4월 검증 범위를 기준으로 시작하고, 이후 다른 월과 상품군으로 확장한다.

## 남은 업무 질문

PRD/TRD/UI 확정 전 작성자 인터뷰로 확인해야 할 것:

- `P00000YU / -` 판매수 1은 어느 L에 반영해야 하는가?
- 컵비즈는 1kg 합계에 포함해야 하는가, 분리해야 하는가?
- `1박스 18개`, `3EA`, `15EA`, `24개` 같은 상품의 환산 기준은 무엇인가?
- L 원가는 어디서 가져오며, 월별로 바뀌는가?
- LU 매핑이 기간별로 바뀔 수 있는가?
