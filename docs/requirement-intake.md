# 요구사항 인박스

## 목적

새 요구사항, 업무 규칙, 인터뷰 확인사항, cafe24 검증 중 발견된 문제를 먼저 기록하는 문서다.

이 문서에 적었다고 바로 구현하거나 PRD/TRD/UI에 반영되는 것은 아니다. 승인된 항목만 설계 문서로 승격한다.

## 운영 원칙

- 사용자 원문과 업무 맥락을 함께 남긴다.
- 엑셀 분석, cafe24 검증, 작성자 인터뷰, UI 설계 중 나온 요구를 모두 기록한다.
- 요구사항은 PRD/TRD/UI/UX/인터뷰/보류로 분류한다.
- 구현이 필요한 항목은 별도 작업 단위로 분리한다.

## 템플릿

```markdown
### REQ-YYYYMMDD-번호: {짧은 이름}

```

- 출처: 사용자 설명

- 업무 맥락: 기존 엑셀은 업무 규칙을 이해하기 위한 참고자료다. 실제 시스템 화면은 엑셀의 셀 구조를 그대로 복제할 필요가 없다.

- 기대 결과: 월별 요약, L 기준 집계, 미확정 매핑, 불일치 항목을 먼저 보여주고 상세 U 옵션 내역은 펼쳐보는 구조로 설계한다.
- 영향 문서: `docs/prd-trd-ui-prompt-draft.md`
- 우선순위: P1
- 다음 결정: PRD/TRD/UI 프롬프트 초안에 반영했다.

### REQ-20260624-01: Cafe24 조회값의 0/확인불가/기준값 상태를 보존한다

- 상태: TRD 후보 / UI 후보 / UX 후보 / 데이터 검증 후보
- 출처: 사용자 설명 / UI 검토 / cafe24 검증
- 사용자 원문:
  > 값 읽을 수 없으면 0으로 표시하면 안돼. 이렇게 0으로 표시를 하면 실제값으로 오해를 하게 돼!!
  > 절대로 이렇게 표시하면 안돼. 값을 못갖고 온것과 읽은값을 확실하게 구분해서 표시가 되어야 돼.
  > 매우 매우 중요한 원칙이다.
  >
  > 직접판매셀만 값을 읽어오는 것은 아니야. 다른 셀들도 읽어와. 너 지금 문제를 너무 협소하게 판단해.
  > cafe24에서 읽어오는 모든 값들에 적용되어야 하는 규칙이야!!!
- 업무 맥락:
  `상품코드` 페이지에 `세트할인 구조설계` 탭의 L상품을 추가하면서, Cafe24 기간 판매 응답에 없는 상품/옵션의 직접판매 수량을 어떻게 해석할지 문제가 드러났다. Cafe24 판매 리포트는 해당 기간 판매 기록이 없는 옵션을 응답하지 않을 수 있으므로, 기준표에서 상품/옵션 존재가 확인되면 기간 응답 누락은 판매수량 0으로 해석한다. 이 문제는 직접판매 셀에 한정되지 않고 Cafe24에서 읽어오는 모든 값과 계산 결과, Excel 다운로드까지 영향을 준다.
- 현재 문제:
  기간 판매 없음, 조회 실패, 기준표 보강값, 실제 Cafe24 조회값 0이 같은 UI/Excel 표현으로 섞이면 사용자가 판매수량, 매출, 합계, 기준값을 잘못 판단할 수 있다. 특히 상품/옵션 존재가 확인되지 않은 값을 0으로 표시하거나 계산하면 데이터 무결성 문제가 된다.
- 기대 결과:
  - `0`은 Cafe24에서 실제로 읽은 값이 0이거나, 기준표에서 존재가 확인된 상품/옵션이 해당 기간 Cafe24 판매 응답에 없을 때 표시한다.
  - 상품/옵션 존재 자체가 확인되지 않거나 API 실패/응답 중단 등으로 값을 신뢰할 수 없으면 별도 확인불가 상태로 표시하고 0으로 계산하지 않는다.
  - 기준표/로컬 fallback 값은 Cafe24 조회값과 구분한다.
  - 상품명, 옵션명, 단가, 직접판매, 매핑 수량, 총판매, 매출, 소계, 합계 등 Cafe24 조회 기반 값 전체에 상태/출처가 보존된다.
  - 화면과 Excel 다운로드에서 동일한 업무 맥락이 유지된다.
  - Excel 계산식은 텍스트 상태값으로 깨지지 않으며, 확인불가 포함 합계는 `확인불가 제외 합계`임을 알 수 있다.
- 영향 문서:
  `docs/cafe24-read-value-state-policy.md`, 향후 TRD/UI/UX 설계 문서, Excel 다운로드 규칙, E2E 검증 기준
- 우선순위: P0
- 다음 결정:
  상세 정책 초안은 `docs/cafe24-read-value-state-policy.md`에 기록했다. 구현 전 아래 사항을 승인해야 한다.
  1. 화면의 좁은 숫자 셀에서 확인불가 표시 방식
  2. Excel 상태 보존 방식(상태 컬럼/주석/범례)
  3. 기존 Excel 좌표계 유지 범위
  4. 기준표 단가의 계산 사용 조건
  5. 상품코드 페이지 우선 적용인지 공통 데이터 모델 확장인지

### REQ-20260624-02: 상품코드 페이지 보기 모드로 좁은 화면 UX를 개선한다

- 상태: PRD 후보 / UI 후보 / UX 후보
- 출처: 사용자 설명 / UI 검토
- 사용자 원문:
  > 사용자가 원하면 좁은 모니터 화면에서도 U상품을 화면에 더 많이 한번에 볼 수 있게 하면 좋겠어.
  > 그러려면 상품코드~직접판매 영역을 적절하게 숨겼다가 펼쳤다가 해야 할것 같다.
  > 사용자는 특정 칼럼만 숨기길 원할 수도 있고.
  >
  > 사용자 UX관점에서 보기 쉽게 원하는 대로 표시해주는 구현이야. 핵심주제는 사용자 UX 증대이다.
  > 이 관점에서 분석해
- 업무 맥락:
  `상품코드` 페이지는 왼쪽 상품 정보 영역과 오른쪽 숫자 영역을 한 화면에 함께 보여준다. 좁은 모니터에서는 왼쪽 고정 영역이 넓어 오른쪽 숫자 컬럼을 한 번에 많이 보기 어렵고, 사용자는 교차셀 비교를 위해 수평 스크롤을 반복해야 한다.
- 현재 문제:
  현재는 수평 스크롤 시 왼쪽 영역이 자동 compact 처리되지만, 사용자가 작업 목적에 맞게 `상품코드~직접판매` 영역을 직접 접거나 펼칠 수 없다. 사용자가 특정 컬럼만 숨기고 싶어도 이를 표현할 UI가 없다.
- 기대 결과:
  - 사용자는 작업 목적에 맞게 `기본`, `넓게`, `더 넓게` 보기 모드를 선택할 수 있다.
  - 좁은 화면에서도 오른쪽 숫자 영역을 더 많이 볼 수 있다.
  - 상품/옵션의 식별 맥락은 완전히 잃지 않는다.
  - 필요하면 상품명, 옵션명, 단가, 직접판매 같은 왼쪽 정보 컬럼을 다시 확인할 수 있다.
  - 1차는 단순한 보기 모드 중심으로 구현하고, 컬럼별 사용자 지정은 후속 단계로 분리한다.
- 영향 문서:
  `docs/product-codes-view-mode-design.md`, 상품코드 페이지 UI 설계, E2E 검증 기준
- 우선순위: P1
- 다음 결정:
  사용자 검토를 위해 요구사항과 설계안을 `docs/product-codes-view-mode-design.md`에 초안으로 작성한다. 승인 후 문서를 먼저 커밋하고, 이후 구현 작업을 별도 커밋으로 진행한다.

### REQ-20260625-01: 세트상품 구성 단가를 매출 수식에서 추적 가능한 변수로 참조한다

- 상태: 설계 초안 작성 / 구현 승인 대기
- 출처: 사용자 설명 / UI 검토 / 수식 추적성 검토
- 사용자 원문:
  > BL계산상에 보면 이렇게 세트 구성 단가가 숫자로 박혀 있어.
  > 하지만 이는 엑셀표에는 나와있진 않지만, 아래의 모달에 정의되어 있는 변수값이다.
  >
  > 맞아. 이렇게 숫자로 박혀 있으면 추적성에 문제가 있고, 추후에 가격이 변경되면 수동으로 수식을 바꿔줘야 하는 문제가 있어. 따라서 이를 변수처리해야 하는게 적절한다.
- 업무 맥락:
  `상품코드` 페이지의 BL열 `매출` 수식은 직접판매 매출과 위쪽상품 기여 매출을 합산한다. 세트상품 기여 매출 항은 세트상품 구성 편집 모달에 정의된 구성품별 `수량`, `세트가`를 기준으로 계산된다. 예를 들어 `BL11 = F11*E11 + BG11*21040`에서 `21040`은 `P00000YS / A` 세트상품을 구성하는 `P00000HT / A`의 세트가다.
- 현재 문제:
  - BL열 수식에 `21040` 같은 세트 구성 단가가 숫자 literal로 직접 박혀 있어, 사용자가 수식만 보고 해당 값의 출처를 추적하기 어렵다.
  - 세트상품 구성 편집 모달에서 세트가가 변경되면, 화면 수식과 Excel 다운로드 수식이 같은 원천값을 참조한다는 보장이 약하다.
  - Excel 다운로드 후 사용자가 세트 구성 단가를 검토하거나 수정하려 할 때, 어떤 수식 항이 어떤 세트 구성 정의에서 왔는지 업무 맥락이 드러나지 않는다.
  - 하드코딩된 숫자처럼 보이기 때문에 감사, 검산, 가격 변경 대응에서 수동 수정 누락 위험이 생긴다.
- 기대 결과:
  - 세트상품 구성 단가는 매출 수식 안의 숫자 literal이 아니라, 세트상품 구성 정의에서 온 추적 가능한 변수/참조값으로 표현한다.
  - 화면의 수식 표시와 Excel 다운로드 수식은 동일한 단가 원천을 참조해야 한다.
  - 사용자는 `BL11` 같은 매출 수식에서 세트 구성 단가가 어느 세트상품/옵션/왼쪽상품/옵션의 세트가인지 추적할 수 있어야 한다.
  - 세트상품 구성 편집 모달에서 세트가를 변경하면, 해당 값을 참조하는 매출 계산과 Excel 수식이 일관되게 갱신되어야 한다.
  - Excel 파일만 열어도 세트 구성 단가의 출처와 값이 보존되어야 하며, 수식 계산이 깨지지 않아야 한다.
  - 직접판매 단가(`E행`)와 세트 구성 단가는 서로 다른 원천값임을 사용자가 구분할 수 있어야 한다.
- 제약 및 설계 고려:
  - 기존 엑셀 좌표계와 BL열 매출 수식의 업무 의미는 유지한다.
  - 세트 구성 단가 참조 방식은 Excel에서도 계산 가능한 형태여야 한다.
  - 숨겨진 시트, 이름 정의(named range), 보조 가격 테이블, 화면 전용 변수명 중 어떤 방식을 쓸지는 별도 설계에서 결정한다.
  - 세트 구성 단가가 여러 구성품에 중복 사용되거나 같은 L상품/옵션이 여러 세트상품에 포함되는 경우에도 참조가 모호하면 안 된다.
  - 사용자가 세트상품 구성 편집 모달에서 값을 바꿨을 때 화면 계산, 수식 표시, Excel 다운로드가 같은 결과를 내야 한다.
- 영향 문서:
  `docs/product-codes-set-price-reference-design.md`, `docs/hardwax-excel-coordinate-transition-plan.md`, `docs/lu-rule-contract.md`, 상품코드 페이지 TRD/UI 설계, Excel 다운로드 규칙, E2E 검증 기준
- 우선순위: P0
- 검증 기준:
  1. `BL11` 같은 매출 수식에서 세트 구성 단가가 숫자 literal로만 남지 않는다.
  2. 수식 표시 UI에서 세트 구성 단가의 출처를 사용자가 추적할 수 있다.
  3. Excel 다운로드 파일에서 세트 구성 단가 참조가 유지되고 Excel 계산 결과가 기존 계산값과 일치한다.

### REQ-20260625-02: 모든 계산식 셀에 사용자용 계산 해설을 제공한다

- 상태: 요구사항 정제 / 설계 필요
- 출처: 사용자 설명 / Hawkeye UX 검토 / 수식 표시 UX 검토
- 사용자 원문:
  > 매출을 클릭하면 수식이 나와.
  >
  > =F11*E11+BG11*세트 구성 단가[P00000YS/A->P00000HT/A]
  >
  > 하지만 이 수식은 사용자 관점에서는 바로 이해하기 힘들어.
  > 엑셀에 보면 이런 수식들이 여러개 있는데, 사용자가 이해하려면 여기 저기 자료들을 찾아 봐야돼.
  >
  > 사용자 UX에서는 최악이야.
  >
  > 넌 지금 매출만 얘기하고 있는데, 나머지 엑셀식들에도 적용할 생각은 하고 있는거지?
  >
  > 수식이 계산되는 모든곳에 적용되어야 돼.
- 업무 맥락:
  `상품코드` 페이지는 엑셀 좌표계와 수식을 유지하지만, 사용자는 `BG11`, `세트 구성 단가[P00000YS/A->P00000HT/A]`, `전환 단가[...]` 같은 내부 참조만 보고 업무 의미를 즉시 이해하기 어렵다. 수식 원문은 데이터 무결성과 Excel 추적성에는 필요하지만, 사용자에게는 계산 결과가 왜 나왔는지 설명하는 기본 UI가 필요하다.
- 현재 문제:
  - 수식 셀 선택 시 원문 수식이 먼저 노출되어 사용자가 계산 의미를 바로 이해하기 어렵다.
  - 사용자가 수식 항의 의미를 파악하려면 위쪽상품, 왼쪽상품, 세트 구성 모달, 보조 참조명, 엑셀 다운로드 결과를 오가며 확인해야 한다.
  - `매출`처럼 복잡한 셀뿐 아니라 `총판매`, 교차셀, 합계행, 카테고리 합계, 전체 합계 등 수식이 계산되는 모든 곳에서 같은 문제가 발생할 수 있다.
  - 일부 수식만 친절하게 해설하고 다른 수식은 원문만 보여주면 UI 일관성과 사용자 신뢰가 깨진다.
  - 원문 수식 문자열을 사람이 읽기 좋게 후처리하는 방식은 패턴 변경에 취약하고, 업무 의미를 안정적으로 보존하기 어렵다.
- 정제된 요구사항:
  - `상품코드` 페이지에서 수식이 계산되는 모든 셀은 원문 수식만 보여주지 않고, 사용자용 계산 해설을 함께 제공한다.
  - 적용 대상은 특정 컬럼이 아니라 `매출`, `총판매`, 교차셀, 합계행, 카테고리 합계, 전체 합계, 직접판매 기반 계산, 전환상품 기반 계산, 세트상품 구성 기반 계산, 전환 단가 참조, 세트 구성 단가 참조, 향후 추가될 모든 계산식 셀이다.
  - 원문 수식은 Excel 호환성, 데이터 무결성, 추적성을 위해 유지한다.
  - 사용자에게는 원문 수식보다 먼저 사람이 읽을 수 있는 계산 요약과 계산 항목을 보여준다.
  - 계산 해설은 모든 수식 셀에서 같은 패턴을 사용한다.
  - 계산 해설은 구분, 기준 상품/옵션, 참조 셀, 수량, 단가, 금액, 합계가 드러나는 구조를 가져야 한다.
  - 원문 수식은 `원문 수식 보기` 같은 보조 정보로 제공한다.
- UX 표시 원칙:
  - 기본 위치는 기존 상단 선택 정보 영역이다.
  - 셀 선택 시 상단 고정 영역에 계산 요약을 먼저 표시한다.
  - 상세 내역은 같은 영역의 펼침 패널로 제공한다.
  - 원문 수식은 기본 설명보다 낮은 위계의 접힘 영역으로 제공한다.
  - 계산 해설 확인은 반복적으로 수행되는 조회 흐름이므로 기본 UI를 모달로 띄우지 않는다.
  - 모달은 필요 시 `자세히 보기` 또는 감사/검산용 상세 분석 UI로만 검토한다.
  - 표와 선택 셀 맥락을 가리지 않아야 하며, 수평/수직 스크롤 중에도 선택 셀의 계산 의미를 확인할 수 있어야 한다.
- 설계 원칙:
  - 수식 문자열을 파싱해서 해설을 만들지 않는다.
  - 계산을 만드는 내부 모델에서 사용자용 해설 데이터를 함께 생성한다.
  - 화면 표시 수식, 사용자용 계산 해설, Excel 다운로드 수식은 같은 계산 원천에서 생성되어야 한다.

  - 같은 계산 의미는 화면 어디서나 같은 명칭과 같은 UI 패턴으로 표시한다.
- Hawkeye PASS 기준:

  - 사용자가 다른 문서, 엑셀 시트, 모달, 참조표를 찾아다니지 않아도 1차 계산 의미를 파악할 수 있다.

  - 원문 수식도 필요할 때 확인 가능해야 한다.

### REQ-20260625-03: 서버 재시작은 개발/운영 서비스 전체를 정상 상태로 복구한다

- 상태: 요구사항 정제 / 설계 필요
- 출처: 사용자 장애 보고 / Root Cause Auditor 관점 조사 / 개발서버 재시작 흐름 검토
- 사용자 원문:
  > 서버 재시작후 상품코드를 가보면 오류가 나.
  >
  > 재시작후 서버가 아예 죽은거 같다
  >
  > 서버 재시작하면 서비스가 제대로 서비스가 재시작되도록 해야돼.
- 업무 맥락:
  홈 화면의 `서버 재시작` 기능은 사용자가 현재 실행 중인 catchup 서비스를 다시 정상 상태로 만들기 위한 관리 기능이다. 사용자는 이 버튼을 누른 뒤 `상품코드` 페이지 같은 주요 업무 화면으로 이동했을 때 서비스가 계속 사용 가능하다고 기대한다. 개발 환경에서도 이 기대는 동일하다. 프론트엔드와 백엔드 중 하나만 살아 있는 상태는 사용자가 보기에는 서비스 장애다.
- 관측된 장애:
  - 서버 재시작 후 홈 화면은 열리지만 `상품코드` 페이지 진입 시 `상품코드 조회 요청을 시작하지 못했습니다`, `백엔드 서버에 연결할 수 없습니다`, `Failed to fetch` 오류가 표시된다.
  - 실제 조사 시 `127.0.0.1:8000` 백엔드는 살아 있었지만 `127.0.0.1:5173` 프론트엔드 개발 서버는 종료되어 있었다.
  - 현재 로컬 개발 환경에는 `pm2`가 없고, 백엔드 `/api/admin/restart`는 백엔드 프로세스만 새로 띄운다.
  - `npm run dev`의 개발 서버 감독 스크립트는 백엔드 자식 프로세스가 종료되면 프론트엔드도 함께 종료한다.
  - 결과적으로 재시작 버튼이 개발 환경에서 `백엔드 단독 실행 + 프론트엔드 종료`라는 불완전한 상태를 만들 수 있다.
- 현재 문제:
  - `서버 재시작`이라는 사용자 표현과 실제 동작 범위가 일치하지 않는다.
  - 개발 환경에서 백엔드만 재시작하는 API가 전체 개발 서버 생명주기를 알지 못한다.
  - 프론트엔드 단독, 백엔드 단독, 프록시 불능 상태를 재시작 성공으로 오해할 수 있다.
  - 이전에 프론트엔드가 백엔드 부재를 감지하도록 보강했더라도, 재시작 자체가 프론트엔드를 죽이는 경로는 차단하지 못한다.
  - 서버 재시작 후 `5173`과 `8000`이 함께 살아 있는지 검증하는 회귀 테스트가 부족하다.
- 기대 결과:
  - 개발 환경에서 `서버 재시작` 후 `127.0.0.1:5173` 프론트엔드와 `127.0.0.1:8000` 백엔드가 함께 정상 동작해야 한다.
  - `http://127.0.0.1:5173/catchup/#product-codes` 진입 후 상품코드 조회가 정상 시작되어야 한다.
  - 프론트엔드가 백엔드보다 먼저 뜨거나 백엔드가 준비되기 전에 조회가 시작되어도, 사용자는 깨진 화면이 아니라 준비 중/재시도 가능한 상태를 보아야 한다.
  - 재시작 기능이 개발 환경에서 전체 서비스를 안전하게 재시작할 수 없다면, 버튼은 성공처럼 동작하지 않고 명확한 안내와 대체 조치를 제공해야 한다.
  - 운영 환경의 `pm2 restart` 경로와 개발 환경의 `npm run dev` 경로는 서로 다른 생명주기 계약을 명확히 가져야 한다.
  - 어떤 경로에서도 `백엔드만 살아 있고 프론트엔드가 죽은 상태`, `프론트엔드만 살아 있고 백엔드가 죽은 상태`, `프록시만 실패하는 상태`가 재시작 완료 상태로 남으면 안 된다.
- 정제된 요구사항:
  - `서버 재시작`은 단일 프로세스 재실행이 아니라 사용자가 접속하는 서비스 단위의 복구 기능으로 정의한다.
  - 개발 진입점, 운영 진입점, UI 재시작 버튼, 백엔드 재시작 API, 문서, 테스트는 같은 재시작 원칙을 따라야 한다.
  - 개발 환경에서 UI가 호출하는 재시작 기능은 `npm run dev`로 띄운 프론트엔드/백엔드 감독 구조와 충돌하면 안 된다.
  - 재시작 API는 현재 실행 모드가 개발 감독 모드인지, 운영 PM2 모드인지, 백엔드 단독 모드인지 구분해야 한다.
  - 지원하지 않는 실행 모드에서는 재시작을 수행하지 않고 사용자가 이해할 수 있는 오류/안내를 반환해야 한다.
  - 재시작 완료 판단은 프로세스 생성 성공이 아니라 실제 서비스 health check 성공이어야 한다.
  - 프론트엔드 화면은 백엔드 준비 전 조회 실패를 영구 오류로 고정하지 않고, 재시도/준비 중 상태를 제공해야 한다.
- Root Cause Auditor PASS 기준:
  - 개발서버 실행 진입점 전체가 확인되었다.
  - 프론트엔드 단독 실행 가능성과 백엔드 단독 실행 가능성이 모두 확인되었다.
  - 백엔드 준비 전 프론트엔드가 먼저 떠서 502 또는 `Failed to fetch`가 발생하는 경로가 차단되었다.
  - UI 재시작 버튼, 백엔드 재시작 API, 개발 스크립트, 운영 스크립트, 문서, 테스트가 같은 원칙을 강제한다.
  - 실제 실행 시 `5173`과 `8000`이 함께 살아나고, `상품코드` 조회가 통과한다.
  - 재시작 실패 시 사용자는 다음 행동을 알 수 있는 메시지를 본다.
- 검증 기준:
  1. `npm run dev` 또는 공식 개발 서버 시작 명령 후 `127.0.0.1:5173`과 `127.0.0.1:8000`이 모두 listening 상태다.
  2. `/api/version`, `/catchup/api/version`, `상품코드` 조회 API가 모두 정상 응답한다.
  3. 홈 화면에서 `서버 재시작`을 수행한 뒤에도 `5173`과 `8000`이 모두 정상 상태로 복구된다.
  4. 재시작 직후 백엔드 준비 지연이 있어도 상품코드 페이지는 복구 가능한 준비/재시도 UX를 제공한다.
  5. `pm2`가 없는 개발 환경에서 백엔드만 단독 재시작되어 프론트엔드가 종료되는 경로가 재현되지 않는다.
  6. 백엔드 단독 실행 상태에서 UI 재시작 요청이 들어오면 성공처럼 처리하지 않고 명확한 안내를 반환한다.
  7. 회귀 테스트는 정상 재시작, 백엔드 준비 지연, 프론트엔드/백엔드 중 하나만 살아 있는 비정상 상태, 상품코드 조회 복구를 포함한다.

### REQ-20260626-01: 세트상품 교차셀 더블클릭은 기존 구성 확인/수정에만 사용한다

- 상태: 구현 완료 / Hawkeye PASS
- 출처: 상품코드 화면 BG12 더블클릭 UX 검토
- 사용자 원문:
  > 이렇게 어려운 모달을 띄워야 할까?
  >
  > 더블클릭을 해서 모달을 띄운다면, 분명히 의미가 있어야 돼. 그렇지 않다면 노이즈일뿐이다
- 업무 맥락:
  상품코드 화면의 세트상품 컬럼은 위쪽 U상품 영역에 표시되고, 세트상품 구성 추가/삭제/전체 편집은 이미 세트상품 컬럼 제목 클릭으로 진입할 수 있다. 교차셀 더블클릭은 사용자가 특정 셀 값의 의미를 확인하려는 강한 액션이므로, 관계가 없는 빈 셀에서 큰 편집 모달을 띄우면 노이즈가 된다.
- 정제된 요구사항:
  - 세트상품 교차셀에 값이 있고 실제 세트 구성품과 연결되어 있으면 더블클릭 시 세트상품 구성 편집 모달을 연다.
  - 이때 모달은 세트상품 컬럼 제목 클릭과 같은 전체 편집 모달을 사용하되, 더블클릭한 L상품/옵션 구성 행을 강조하고 수량 입력에 포커스한다.
  - 세트상품 빈 교차셀은 더블클릭해도 모달을 띄우지 않는다. 셀 선택만 유지한다.
  - 빈 세트상품 교차셀을 구성 추가 후보로 해석하지 않는다.
  - 세트상품 구성 추가/삭제는 세트상품 컬럼 제목의 구성 편집 진입점에서만 수행한다.
  - 전환상품 교차셀 더블클릭은 기존 LU 매핑 변경/해제 흐름을 유지한다.
- UX 원칙:
  - 모달이 뜬다는 것은 사용자가 확인/수정할 기존 관계가 있다는 뜻이어야 한다.
  - 빈 셀에서 모달을 띄워 사용자가 의미를 해석하게 만들지 않는다.
  - 같은 모달을 쓰더라도 컬럼 제목 클릭은 전체 편집, 값 있는 교차셀 더블클릭은 해당 구성 행 드릴다운으로 역할을 구분한다.
- Hawkeye PASS 기준:
  - BG12처럼 빈 세트상품 교차셀을 더블클릭해도 모달이 뜨지 않는다.
  - BG11처럼 값 있는 세트상품 교차셀을 더블클릭하면 세트상품 구성 편집 모달이 열리고 해당 구성 행이 강조/포커스된다.
  - 세트상품 컬럼 제목 클릭은 기존처럼 전체 구성 편집으로 열린다.
  - 전환상품 교차셀 더블클릭은 LU 매핑 모달로 열린다.
  - 세트상품 모달이 열린 상태에서도 모달 밖 배경 엑셀 시트는 이동 가능하다.
- 검증 기준:
  1. 값 있는 세트상품 교차셀 더블클릭 E2E.
  2. 빈 세트상품 교차셀 더블클릭 E2E.
  3. 세트상품 컬럼 제목 편집 E2E.
  4. 전환상품 교차셀 더블클릭 회귀 E2E.
  5. Hawkeye 실제 클릭 검증으로 사용자 관점의 모달 의미, 포커스, 배경 스크롤을 확인한다.
