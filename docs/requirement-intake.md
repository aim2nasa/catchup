# 요구사항 인박스

## 목적

새 요구사항, 업무 규칙, 인터뷰 확인사항, cafe24 검증 중 발견된 문제를 먼저 기록하는 문서다.

이 문서에 적었다고 바로 구현하거나 PRD/TRD/UI에 반영되는 것은 아니다. 승인된 항목만 설계 문서로 승격한다.

## 운영 원칙

- 사용자 원문과 업무 맥락을 함께 남긴다.
- 엑셀 분석, cafe24 검증, 작성자 인터뷰, UI 설계 중 나온 요구를 모두 기록한다.
- 요구사항은 PRD/TRD/UI/UX/인터뷰/보류로 분류한다.
- 구현이 필요한 항목은 별도 작업 단위로 분리한다.

```markdown

- 출처: 사용자 설명 / 엑셀 분석 / cafe24 검증 / 작성자 인터뷰 / UI 검토 / 기타

- 업무 맥락:
- 현재 문제:
- 기대 결과:
- 영향 문서:
- 우선순위: P0 / P1 / P2 / P3
- 다음 결정:
```

## 현재 인박스

### REQ-20260523-01: 엑셀 레이아웃을 그대로 복제하지 않는다

- 상태: 반영 완료
- 출처: 사용자 설명
- 사용자 원문:
  > 엑셀은 참고하는 데이터이지만, 이 엑셀처럼 그대로 보여주는게 아니라 사용자가 쉽게 이해하고 파악할 수 있도록 결과를 내야 한다.
- 업무 맥락: 기존 엑셀은 업무 규칙을 이해하기 위한 참고자료다. 실제 시스템 화면은 엑셀의 셀 구조를 그대로 복제할 필요가 없다.
- 현재 문제: 엑셀형 교차표를 그대로 웹으로 옮기면 사용자가 핵심 결과, 불일치, 미확정 항목을 빠르게 파악하기 어렵다.
- 기대 결과: 월별 요약, L 기준 집계, 미확정 매핑, 불일치 항목을 먼저 보여주고 상세 U 옵션 내역은 펼쳐보는 구조로 설계한다.
- 영향 문서: `docs/prd-trd-ui-prompt-draft.md`
- 우선순위: P1
- 다음 결정: PRD/TRD/UI 프롬프트 초안에 반영했다.

### REQ-20260523-02: 요구사항 수용 구조를 둔다

- 상태: 반영 완료
- 출처: 사용자 설명
- 사용자 원문:
  > 새로운 요구사항이 생기면 이를 체계적으로 수용하는 구조를 추가하고 싶어.
  > 요구사항 -> PRD/TRD/UI/UX 이렇게 반영되는 체계적인 구조.
- 업무 맥락: 작성자 인터뷰, cafe24 검증, UI 설계 과정에서 새 요구사항이 계속 발견될 수 있다.
- 현재 문제: 새 요구를 바로 설계나 구현에 섞으면 범위가 흔들리고 결정 근거가 사라진다.
- 기대 결과: 요구사항 인박스에 먼저 기록하고, 승인된 항목만 PRD/TRD/UI/UX에 승격한다.
- 영향 문서: `docs/requirements-to-design-process.md`, `docs/requirement-intake.md`, `docs/prd-trd-ui-prompt-draft.md`
- 우선순위: P1
- 다음 결정: 공통 프로세스 문서와 인박스 문서를 생성했다.
