# 요구사항 수용 및 설계 반영 프로세스

## 목적

새로운 요구사항이 나올 때마다 바로 PRD/TRD/UI 설계나 구현에 섞어 넣으면 범위가 흔들린다.

이 문서는 새 요구사항을 체계적으로 받아들이고, 승인된 내용만 PRD/TRD/UI/UX 설계에 반영하기 위한 공통 프로세스다.

이 구조는 특정 프로젝트에만 한정하지 않고, 다른 프로젝트에서도 재사용할 수 있는 방식으로 정의한다.

## 기본 원칙

- 새 요구사항은 즉시 구현하지 않는다.
- 먼저 요구사항 인박스에 원문과 맥락을 기록한다.
- 요구사항과 아이디어, 버그, UX 불편, 기술 개선을 구분한다.
- PRD/TRD/UI/UX 문서에는 승인된 요구사항만 반영한다.
- 구현이 필요한 항목은 별도 작업 단위로 분리한다.
- 엑셀, 기존 화면, 기존 시스템은 참고 자료이지 그대로 복제할 대상이 아니다.

## 전체 흐름

```text
요구사항 발견
  -> 요구사항 인박스 기록
  -> 분류
  -> 영향 문서 판단
  -> 승인
  -> PRD/TRD/UI/UX 반영
  -> 구현 작업 분리
  -> 검증
```

## 단계별 정의

### 1. 요구사항 발견

요구사항은 아래 상황에서 생길 수 있다.

- 사용자가 업무 설명 중 새 규칙을 말함
- 기존 엑셀이나 화면에서 논리적 문제를 발견함
- cafe24 검증 중 불일치가 발견됨
- 작성자 인터뷰에서 새 업무 규칙이 확인됨
- UI 설계 중 사용자가 이해하기 어려운 지점이 드러남

### 2. 요구사항 인박스 기록

새 요구사항은 먼저 인박스에 기록한다.

기록할 때는 요약만 하지 말고, 가능하면 사용자의 원문과 발생 맥락을 함께 남긴다.

필수 기록 항목:

- 요구사항 ID
- 상태
- 출처
- 사용자 원문
- 업무 맥락
- 현재 문제
- 기대 결과
- 영향 문서
- 우선순위
- 다음 결정

### 3. 분류

요구사항은 아래 중 하나 이상으로 분류한다.

| 분류 | 의미 |
|---|---|
| PRD 후보 | 제품 목적, 사용자 가치, 기능 범위에 영향을 주는 요구 |
| TRD 후보 | API, 데이터 모델, 집계 로직, 저장 구조에 영향을 주는 요구 |
| UI 후보 | 화면 구조, 정보 배치, 조작 방식에 영향을 주는 요구 |
| UX 후보 | 사용자의 이해, 판단, 흐름, 오류 회복에 영향을 주는 요구 |
| 데이터 검증 후보 | 원천 데이터와 결과 검증 기준에 영향을 주는 요구 |
| 인터뷰 질문 | 작성자나 업무 담당자 확인이 필요한 요구 |
| 보류 | 지금 범위 밖이거나 근거가 부족한 요구 |

### 4. 승격 판단

인박스에 기록된 요구는 바로 설계 문서에 반영하지 않는다.

먼저 아래 질문으로 판단한다.

- 반복적으로 발생할 업무 규칙인가?
- 제품 목적에 영향을 주는가?
- 데이터 구조나 계산 방식에 영향을 주는가?
- 사용자 화면 흐름이 바뀌는가?
- 기존 요구사항과 충돌하는가?
- 지금 MVP 범위에 포함할 것인가?

### 5. 설계 문서 반영

승인된 요구만 각 문서에 반영한다.

| 문서 | 반영 기준 |
|---|---|
| PRD | 사용자 문제, 목표, 기능 범위, 정책이 바뀌는 경우 |
| TRD | 데이터 모델, API, 알고리즘, 검증 방식이 바뀌는 경우 |
| UI 설계 | 화면 구조, 테이블, 필터, 상태 표시가 바뀌는 경우 |
| UX 설계 | 사용자의 업무 흐름, 이해 방식, 오류 회복 방식이 바뀌는 경우 |
| 인터뷰 질문지 | 업무 담당자 확인이 필요한 경우 |

## 요구사항 인박스 템플릿

```markdown
### REQ-YYYYMMDD-번호: {짧은 이름}

- 상태: 인박스 / PRD 후보 / TRD 후보 / UI 후보 / UX 후보 / 인터뷰 필요 / 반영 완료 / 보류
- 출처: 사용자 설명 / 엑셀 분석 / cafe24 검증 / 작성자 인터뷰 / UI 검토 / 기타
- 사용자 원문:
- 업무 맥락:
- 현재 문제:
- 기대 결과:
- 영향 문서:
- 우선순위: P0 / P1 / P2 / P3
- 다음 결정:
```

## 우선순위 기준

| 우선순위 | 기준 |
|---|---|
| P0 | 잘못된 수량, 매출, 원가, 이익을 만들 수 있는 문제 |
| P1 | 핵심 업무 판단을 어렵게 하거나 사용자가 높은 확률로 오해하는 문제 |
| P2 | 업무는 가능하지만 반복 확인 비용이 큰 문제 |
| P3 | 표현, 정리, 편의성 개선 |

## 현재 이미 인박스에 넣어야 하는 요구사항 예

### REQ 예시: 엑셀 레이아웃을 그대로 복제하지 않는다

- 상태: PRD 후보 / UI 후보 / UX 후보
- 출처: 사용자 설명
- 사용자 원문:
  > 엑셀은 참고하는 데이터이지만, 이 엑셀처럼 그대로 보여주는게 아니라 사용자가 쉽게 이해하고 파악할 수 있도록 결과를 내야 한다.
- 업무 맥락: 기존 엑셀은 업무 규칙을 이해하는 참고자료지만, 화면은 더 쉽게 재구성해야 한다.
- 현재 문제: 엑셀형 교차표를 그대로 웹에 옮기면 사용자가 핵심 결과와 문제 항목을 빠르게 파악하기 어렵다.
- 기대 결과: 월별 요약, 미확정 매핑, 불일치 항목, 상세 펼침 구조로 사용자 이해를 우선한다.
- 영향 문서: PRD, UI 설계, UX 설계
- 우선순위: P1
- 다음 결정: PRD/TRD/UI 프롬프트 초안에 반영 완료.

### REQ 예시: 새 요구사항 수용 구조를 둔다

- 상태: PRD 후보 / TRD 후보 / UI 후보 / UX 후보
- 출처: 사용자 설명
- 사용자 원문:
  > 새로운 요구사항이 생기면 이를 체계적으로 수용하는 구조를 추가하고 싶어.
  > 요구사항 -> PRD/TRD/UI/UX 이렇게 반영되는 체계적인 구조.
- 업무 맥락: 업무 분석이 진행되면서 작성자 인터뷰, cafe24 검증, UI 설계 과정에서 새 요구사항이 계속 나올 수 있다.
- 현재 문제: 새 요구를 즉시 설계나 구현에 섞으면 범위가 흔들리고, 결정 근거가 사라진다.
- 기대 결과: 요구사항 인박스에 먼저 기록하고, 승인된 것만 PRD/TRD/UI/UX에 승격한다.
- 영향 문서: PRD, TRD, UI 설계, UX 설계, 요구사항 인박스
- 우선순위: P1
- 다음 결정: 공통 프로세스 문서로 정의.
