# 서버 재시작 생명주기 설계

## 목적

`서버 재시작`은 백엔드 프로세스 하나를 다시 띄우는 기능이 아니라, 사용자가 접속하는 catchup 서비스가 정상 사용 가능한 상태로 돌아오는 복구 기능이다.

개발 환경의 서비스 단위는 다음을 모두 포함한다.

- 프론트엔드 개발 서버: `127.0.0.1:5173`
- 백엔드 API 서버: `127.0.0.1:8000`
- 프론트엔드 프록시: `/catchup/api/* -> 127.0.0.1:8000/api/*`

따라서 재시작 후 `8000`만 살아 있고 `5173`이 죽어 있거나, `5173`만 살아 있고 API 프록시가 실패하는 상태는 성공이 아니다.

## 근본 원인

기존 `/api/admin/restart`는 `pm2`가 없으면 백엔드가 자기 자신을 새로 실행하고 종료했다.

하지만 개발 서버는 `scripts/dev.mjs`가 백엔드와 프론트엔드를 함께 감독한다. 이 상태에서 백엔드 자식 프로세스가 종료되면 감독 스크립트는 장애로 판단하고 프론트엔드도 함께 종료한다. 이후 백엔드는 단독으로 다시 떠서 `8000`만 살아 있고 `5173`은 죽은 상태가 된다.

즉, 문제는 백엔드 재시작 자체가 아니라 재시작 책임이 서비스 전체를 아는 상위 감독 프로세스가 아닌 백엔드 내부에 있었던 것이다.

## 설계 원칙

1. 백엔드는 개발 모드에서 자기 자신을 직접 재시작하지 않는다.
2. 개발 모드 재시작은 `scripts/dev.mjs`가 담당한다.
3. 백엔드 `/api/admin/restart`는 개발 모드에서 재시작 요청 파일만 남긴다.
4. `scripts/dev.mjs`는 요청 파일을 감지하면 백엔드만 의도적으로 재기동하고 프론트엔드는 유지한다.
5. 재시작 완료 기준은 프로세스 생성이 아니라 health check 통과다.
6. 지원하지 않는 실행 모드에서는 재시작을 성공처럼 처리하지 않는다.

## 실행 모드별 동작

### 개발 감독 모드

조건:

- 백엔드 환경변수 `CATCHUP_DEV_RESTART_FILE`이 설정되어 있다.
- 이 값은 `scripts/dev.mjs`가 백엔드를 실행할 때 주입한다.

동작:

1. UI가 `/api/admin/restart`를 호출한다.
2. 백엔드는 `CATCHUP_DEV_RESTART_FILE` 경로에 재시작 요청 파일을 기록한다.
3. 백엔드는 종료하지 않고 요청 접수 응답을 반환한다.
4. `scripts/dev.mjs`가 요청 파일을 감지한다.
5. `scripts/dev.mjs`가 백엔드 자식 프로세스를 의도적으로 종료한다.
6. 백엔드가 다시 기동되고 `/api/version` health check가 통과할 때까지 기다린다.
7. 프론트엔드 프록시 `/catchup/api/version` health check를 확인한다.

프론트엔드 서버는 유지한다. 사용자가 보고 있는 화면을 불필요하게 죽이지 않는 것이 개발 UX에 더 적합하다.

### 운영 PM2 모드

조건:

- `pm2`가 설치되어 있다.

동작:

- 백엔드는 `pm2 restart catchup` 요청을 백그라운드에서 실행한다.
- 운영 재시작 완료 여부는 운영 health check로 확인한다.

### 백엔드 단독 모드

조건:

- `pm2`가 없다.
- `CATCHUP_DEV_RESTART_FILE`도 없다.

동작:

- 백엔드는 재시작을 수행하지 않는다.
- HTTP 409와 함께 현재 실행 모드에서는 안전한 재시작을 할 수 없다는 메시지를 반환한다.

이 모드에서 백엔드가 자기 자신만 재시작하면 같은 장애가 재발할 수 있으므로 금지한다.

## UX 원칙

- 재시작 요청 접수와 재시작 완료는 구분한다.
- 실패할 수 있는 모드에서는 성공 알림을 보여주지 않는다.
- 사용자가 다음 행동을 알 수 있는 메시지를 제공한다.
- 재시작 직후 상품코드 페이지가 backend 준비 지연으로 깨지면 안 된다.

## 회귀 테스트 기준

1. 개발 서버 스크립트가 백엔드에 `CATCHUP_DEV_RESTART_FILE`을 주입한다.
2. 백엔드 재시작 API는 개발 모드에서 요청 파일을 쓰고 자기 자신을 종료하지 않는다.
3. 백엔드 재시작 API는 백엔드 단독 모드에서 HTTP 409를 반환한다.
4. 개발 서버 스크립트는 요청 파일 감지 후 백엔드를 재기동하고 frontend proxy health를 확인한다.
5. 코드에 `sys.executable, *sys.argv` 방식의 백엔드 단독 재시작 경로가 남아 있지 않다.

## Root Cause Auditor PASS 기준

- 개발서버 실행 진입점 전체가 같은 원칙을 따른다.
- frontend 단독, backend 단독, backend 준비 전 frontend 조회 실패 경로가 차단되거나 사용자에게 명확히 안내된다.
- 실제 실행 시 `5173`과 `8000`이 함께 살아난다.
- `상품코드` 페이지 조회가 재시작 후에도 통과한다.
- 문서와 테스트가 같은 재시작 생명주기 계약을 강제한다.
